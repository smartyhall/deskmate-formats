# Historical DeskMate utilities and independent format validation

Research proposal following the 2026-11-23 planning discussion; standing policy is subject to separate explicit operator approval. [Initial qualification campaign #178](https://github.com/smartyhall/deskmate-formats/issues/178). After the initial survey and environment qualification, consider this as a secondary workstream, selecting focused experiments that complement active format research under existing authorization.

The objective is to use original diagnostic, conversion, playback, printing, and companion utilities as independently observable implementations, not to assume that their behavior defines a universal DeskMate specification. Some tools may share Tandy libraries or code, others are independent implementations, and a utility may normalize, discard, or silently accept unsupported data. Keep these distinctions explicit.

## Phase A — initial qualification campaign

### Broad utility survey

For each relevant utility or release, record a catalog ID, archive/member identities and hashes, exact product and build strings, author/publisher, readme/help and source-code availability, licensing status, launch commands, runtime and DOS/Windows dependencies, documented input/output formats and supported operations. Record observed modes separately from claimed compatibility. Distinguish a native DeskMate PDM/ACC from a standalone DOS or Windows program and a bundled runtime. Record known-good specimen locations and the smallest repeatable experiment, including untested or blocked entries. Include all utility families below; record other newly cataloged games, educational programs, and productivity companions in the overview but do not turn this campaign into a full application survey.

### Reusable private laboratory environments

Use existing sealed 86Box baselines and private working copies, not a new full-size disk image per utility. Prioritize a generic DeskMate 3.05 environment with the measured Filer/Calendar/Address Book/Draw controls; a separate RSX OEM 03.04.04 environment with Home Organizer, Sound, and Print Companion; 3.00/3.02/3.03.01 controls as justified by actual compatibility; early DeskMate I/II and Personal DeskMate profiles for early converters and DeskHelp; a minimal DOS environment for command-line utilities, BASIC, and utilities shipping their own runtime; and the existing Windows 98 SE/VB6 checkpoint for DM_Music and MidiMapper. Use hardware-matched profiles where available; explicitly label compatibility substitutes. HomeWord II 1.20 needs an isolated runtime and original-app synthetic controls. Preserve original archives, verified installed copies, and checkpoint hashes. Avoid unnecessary duplicate storage and follow [lab storage guidance](lab-storage-housekeeping.md).

Use visible 86Box, the authenticated socket, existing FAT staging/extraction, emulated audio capture, and binary File (LPT) transport. All legacy executables run inside guests, offline, with no physical printer or unrelated host device connected. Use pinned source copies read-only where practical, separate writable targets, exact DOS paths and a fresh job sink; record all unexpected file changes. Check timeouts and recovery from hangs without touching another owned process. Do not replace a native application's runtime with a utility's runtime. Keep recipes/configuration identities and reusable runbooks in the project; original media, raw disk images, private paths, full captures and historic source remain private.

### Qualification gates

Before the first launch, pin the exact archive and executable/member SHA-256, reported version, runtime and guest profile; record any mismatch or unavailable identifier as a blocker rather than substituting another build. A utility is qualified for a particular operation only after a known-good synthetic control and a reproducible output or diagnosis have been observed. Start with one meaningful smoke test per utility, or record the actual blocker, rather than exhaustively decoding it. A launch, menu screenshot, or successful process exit alone is not functional qualification. Run a no-change control first where applicable, then one controlled change, and repeat on a fresh copy. Prioritize DBrepair and Fil2dbf, with a representative printing/audio/conversion smoke test if capacity permits. For previous DM_Music qualification, reuse the recorded native results rather than rerun the full existing matrix.

### DBrepair: first high-value independent validation matrix

Use a pinned native Filer synthetic file, its exact original hash and independently decoded logical records. First verify a known-good copy, save/exit normally, and check every modified file. If DBrepair rewrites healthy data, distinguish benign metadata or normalization from unexpected logical changes. Confirm actual semantics of any repair command before running it.

Construct a deliberately defective copy by changing exactly one known field, with expected byte differences and independent validation of the intended mutation. Prioritize record count, index/address entry, data or index page-chain pointer, duplicate or out-of-order ID, next-ID-like token, orphaned page, and schema descriptor; add record length/separator corruption and residual deleted bytes only when the originating profile supports a controlled experiment. Include boundary and multi-page controls after the initial one-record trial. Never assume that an inferred field is an authoritative invariant. Keep untouched native, tool-generated valid, intentionally malformed, utility output, and subsequent native-reopen states distinct. Each trial starts from a fresh clone. Save the exact input, mutated byte range, utility version/runtime, screen/diagnostic, output hashes, before/after structural and semantic diff, and native cold-open/re-save result if applicable. Record detection-only, unchanged, repaired with preserved records, normalization, partial recovery, silent data loss, rejected/unsupported, crash/hang, or indeterminate separately. A permissive repair utility is not a proof that a file is valid; neither is our parser's acceptance.

Expand from measured Filer to Calendar, Address Book, Information Center, Financial Notebook, Collections, and other DMDB-like files only after determining which application profile DBrepair accepts and how it handles schema and special directory trailers. Keep the separate fixed Corkboard buffer out of this DB matrix. Distinguish reuse of the identical DBREPAIR.PDM between the two packages from independent implementations; compare actual runtime DMDB components and version identities. Use Fil2dbf as an independent exported-data comparison, not automatically an independent implementation of the database engine.

## Durable results and recurring work

Maintain a machine-readable registry of utility, exact version/hash, environment ID, operation and input profile, source evidence, qualification status, fixture/output references, observations/limits, and reproducible recipe. Maintain a separate prioritized backlog keyed to the originating format, with prerequisites and checkpoints. Suggested statuses: archived, identified, environment ready, launched, operation qualified for a named input profile, blocked, and follow-up due. An archived tool is not necessarily a qualified validator. Distinguish native, historical third-party, and our own synthetic controls; independent semantic comparisons should include exact expected values and known lossiness.

Deliver a dated overview, reproducible environment setup and runbooks, registry/backlog, initial highest-value smoke and differential experiments, approved visual exemplars, and narrowly scoped tested tooling where warranted. Preserve eligible synthetic artifacts under the existing manifest/audit rules; do not publish third-party raw source or unreviewed exports. Run applicable portable tests, REUSE, packaging/publication audit, and site checks. Open a review PR; do not self-merge.

After the dedicated qualification campaign, select one or more small, relevant work packages when the primary work and required validation in an already authorized campaign are complete, or directly incorporate a qualified utility comparison into the active format experiment. Prefer the utility most useful to the current research (DBrepair/Fil2dbf during database work, Prn2file/Prtsnd during printing, Sound converters during audio, and so on). Capture the comparison, update the registry and backlog, and checkpoint independently. Do not start a new emulator solely under spare-capacity authority, dispatch extra turns, spend credits, redeem resets, launch unattended runs, or displace primary goals. A separate authorization can schedule a dedicated campaign. This is an ongoing Codex research convention, not a calendar automation.
