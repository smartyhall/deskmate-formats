# Calendar Add Event: partial input and quarter-hour normalization

**Evidence class:** operator-supplied manual UI observations, November 7, 2026,
DeskMate 3.05 running inside **DOSBox-X 2026.08.31**. These are not 86Box
socket experiments and are not new application-generated byte fixtures.
The operator provided before/after screenshots in the research conversation;
those images and matching pre/post disk snapshots are **not archived in this
repository**. No independent file-byte comparison was performed for this note.

## Observed inputs and displayed results

The operator entered event values in the Add Event dialog and inspected the
resulting schedule after saving. The times below are local display values; no
stored UTC offset or timezone was measured.

| Input in Add Event | Displayed schedule time | Notes |
| --- | --- | --- |
| Start `6:` PM, end `7:` PM | 6:00–7:00 PM | Incomplete minute fields |
| Start `04:1` PM, end `04:2` PM | 4:00–4:15 PM | Incomplete minute fields, defaults/normalization not isolated |
| Start `05:05` PM, end `05:08` PM | 5:00–5:15 PM | Complete minute inputs |
| Start `01:05` PM, end `01:13` PM | 1:00–1:15 PM | Complete minute inputs |
| Start `05:08` PM, end `05:31` PM | **5:00–5:45 PM** | Complete inputs on Nov 7; decisive between nearest-quarter and outward-floor/ceiling for this case |

Some entries had a partial date field (for example `11-10/`) while the
displayed schedule was November 10, 2026, and the saved event appeared there.
The source of the omitted year was **not isolated**; possible current-day,
calendar context and system-date defaults remain hypotheses.

Earlier sample entries disappeared from one screenshot **because the operator
intentionally removed them**, not because of observed spontaneous data loss.

## Interpretation and limits

The complete `05:08–05:31` test supports **floor start to the preceding
quarter-hour and ceiling end to the following quarter-hour**, rather than
independent nearest-quarter rounding. Other observed pairs are consistent
with outward rounding. These are **UI-level examples**, not an exhaustive
boundary, minimum-duration or time-encoding characterization.

The observations do **not** establish that the native file format cannot
represent other minute values, that the UI applies the same rule for every
input mode, or that all partial date fields inherit the year the same way.
A targeted byte-level before/after comparison and a small set of boundary
cases would discriminate those alternatives if later needed.

This does not change the existing reader/writer codec or authorize a new native
experiment. The [interoperability contract](../interoperability.md) records a
separate operator-approved **future sync policy**: outward quarter-hour
projection where needed; preserve precise external event values across an
unchanged DeskMate round-trip; treat confirmed DeskMate timing edits as
authoritative for the edited fields. That policy is **not implemented**.
