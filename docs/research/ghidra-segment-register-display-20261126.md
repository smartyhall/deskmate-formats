# The `8E /r` segment-register display defect (2026-11-26)

Ghidra 12.1.4 prints the register form of `MOV Sreg, r/m16` with its operands
reversed. This note reproduces the defect on a self-authored specimen, shows
that the semantics are nevertheless correct, establishes its scope across
operand forms and languages, records that upstream has already reported and
fixed it, and validates the one-line correction in a **separate** installation.

Nothing here depends on a commercial binary: the specimen is generated by
[`tests/fixtures/synthetic/segment_forms.py`](../../tests/fixtures/synthetic/segment_forms.py)
from the Intel encoding, so a mismatch is a decoder or display finding rather
than a property of a particular program.

## The defect

```text
12.1.4 listing          p-code writes        architectural meaning
MOV AX,DS      8E D8    DS                   DS := AX
MOV AX,DS      8C D8    AX                   AX := DS
```

Two different instructions with opposite meanings print the same text. The
listing is not merely terse; it is misleading, and it is exactly the pair a
16-bit real-mode analyst meets when a program sets up its data segment.

## Scope

Specimen decoded at fixed offsets with `x86:LE:16:Real Mode` (offsets 0–32) and
`x86:LE:64:default` (a second payload). "Text" is the listing Ghidra produced;
"writes" is the p-code output register.

| Bytes | Form | 12.1.4 text | p-code writes | Correct? |
| --- | --- | --- | --- | --- |
| `8E D8` | `MOV DS,AX` | `MOV AX,DS` | DS | text reversed |
| `8E C0` | `MOV ES,AX` | `MOV AX,ES` | ES | text reversed |
| `8E D0` | `MOV SS,AX` | `MOV AX,SS` | SS | text reversed |
| `8E E0` | `MOV FS,AX` | `MOV AX,FS` | FS | text reversed |
| `8E E8` | `MOV GS,AX` | `MOV AX,GS` | GS | text reversed |
| `8E C8` | `MOV CS,AX` (reserved) | `MOV AX,CS` | CS | text reversed |
| `8C D8` | `MOV AX,DS` | `MOV AX,DS` | AX | correct |
| `8C C0` | `MOV AX,ES` | `MOV AX,ES` | AX | correct |
| `8C DB` | `MOV BX,DS` | `MOV BX,DS` | BX | correct |
| `8E 1E 34 12` | `MOV DS,[1234h]` | `MOV DS,word ptr [0x1234]` | DS | correct |
| `8C 1E 34 12` | `MOV [1234h],DS` | `MOV word ptr [0x1234],DS` | — | correct |
| `66 8E D8` | `MOV DS,EAX` | `MOV EAX,DS` | DS | text reversed |
| `66 8C D8` | `MOV EAX,DS` | `MOV EAX,DS` | EAX | correct |
| `48 8E D8` | `MOV DS,RAX` | `MOV RAX,DS` | DS | text reversed |
| `48 8C D8` | `MOV RAX,DS` | `MOV RAX,DS` | RAX | correct |
| `8E D8` (64-bit) | `MOV DS,EAX` | `MOV EAX,DS` | DS | text reversed |
| `4D 8E C0` | `MOV ES,R8` | `MOV R8,ES` | ES | text reversed |
| `49 8C D8` | `MOV R8,DS` | `MOV R8,DS` | R8 | correct |

The pattern is exact: **every** `8E` register form is reversed, including the
reserved `CS` encoding; **no** `8C` form and **no** memory form is affected;
the same reversal appears in 16-bit, 32-bit-operand and 64-bit-operand
variants. The defect is in the register form only, because that is the form
whose operands are both registers and therefore both printed from the
constructor name.

## Root cause

The processor language prints a constructor's mnemonic and operands from its
**name**, while the pattern after `is` determines decoding and the semantic
section determines p-code. Commit `f9ed6f4` ("GP-7018: Fixed register opsize
for mov to/from segment registers") split the old

```text
:MOV Sreg,rm16      is ... byte=0x8e; rm16 & Sreg ...   { Sreg=rm16; }
```

into a memory form and three register forms, and named the register forms after
the *source* operand:

```text
:MOV Rmr16,Sreg     is ... byte=0x8e; mod=3 & Rmr16 & Sreg   { Sreg = Rmr16; }
```

The semantic assignment stayed right; the name became the display, so the
printed order follows `Rmr16, Sreg`. The pattern order must stay `Rmr16 &
Sreg` because that is the encoding order of the ModRM fields, which is why the
fix is a rename and not a reordering.

## Independent corroboration

Three sources agree that the *meaning* is `DS := AX`, so the p-code and the
decoder are not in question:

1. **The encoding**, from the Intel instruction set reference: `8E /r` is
   `MOV Sreg, r/m16`, destination first.
2. **Capstone**, decoding the same bytes in the portable test
   (`tests/portable/test_segment_forms.py`) and printing `mov ds, ax`.
3. **Ghidra's own p-code**, which writes the segment register.

Only the listing text disagrees. That is the whole finding, and it is why the
campaign's rule is to read segment-register instructions from the original
bytes and to report their effect from p-code.

## Upstream status

The defect is already reported and already fixed upstream:

* [issue #9635](https://github.com/NationalSecurityAgency/ghidra/issues/9635),
  opened 2026-09-14 against 12.1.3, with the same diagnosis and the same
  one-line patch;
* [#9739](https://github.com/NationalSecurityAgency/ghidra/issues/9739) closed
  as a duplicate;
* [PR #9637](https://github.com/NationalSecurityAgency/ghidra/pull/9637),
  merged as commit `dc1e375` on 2026-10-08 for the 12.2 milestone;
* a comment on the issue confirms 12.1.4 is still affected.

So a new bug report would be a duplicate, and no new report was filed. What
this campaign adds is an independent reproduction on a self-authored specimen,
the full scope table above, and a validated trial of the correction in an
isolated installation.

## Trial correction in a separate installation

The shared installation at `C:\tools\ghidra_12.1.4_PUBLIC` was not modified.
A copy was made at `C:\DeskMateLab\tools\ghidra_12.1.4-segtrial` and only that
copy was changed:

```text
:MOV Sreg,Rmr16   is vexMode=0 & opsize=0 & byte=0x8e; mod=3 & Rmr16 & Sreg   { Sreg = Rmr16; }
:MOV Sreg,Rmr32   is vexMode=0 & opsize=1 & byte=0x8e; mod=3 & Rmr32 & Sreg   { Sreg = Rmr32(0); }
:MOV Sreg,Rmr64   is $(LONGMODE_ON) & opsize=2 & byte=0x8e; mod=3 & Rmr64 & Sreg { Sreg = Rmr64(0); }
```

The three pattern bodies are unchanged; only the constructor names changed.
Compiling with `support/sleigh -a Ghidra/Processors/x86` rebuilt `x86.sla`
(439,288 bytes) and `x86-64.sla` (501,177 bytes) and reported "2 languages
successfully compiled".

Re-running the same specimen against the trial installation:

| Bytes | 12.1.4 | trial | p-code |
| --- | --- | --- | --- |
| `8E D8` | `MOV AX,DS` | `MOV DS,AX` | DS (unchanged) |
| `8E C0` | `MOV AX,ES` | `MOV ES,AX` | ES |
| `8C D8` | `MOV AX,DS` | `MOV AX,DS` | AX |
| `8E 1E 34 12` | `MOV DS,word ptr [0x1234]` | unchanged | DS |
| `66 8E D8` | `MOV EAX,DS` | `MOV DS,EAX` | DS |
| `66 8C D8` | `MOV EAX,DS` | unchanged | EAX |
| `48 8E D8` | `MOV RAX,DS` | `MOV DS,RAX` | DS |
| `8E D8` (64-bit) | `MOV EAX,DS` | `MOV DS,EAX` | DS (unchanged) |
| `4D 8E C0` | `MOV R8,ES` | `MOV ES,R8` | ES |

Decoding did not shift: every instruction kept its offset, length and p-code.
The correction changes display only, which is the expected and desired result.

The patch text is kept in
[`patches/ghidra-12.1.4-mov-sreg-display.patch`](patches/ghidra-12.1.4-mov-sreg-display.patch)
for reference. It is a documentation artifact, not something this repository
applies to anything.

## Regression cases

A fix should be accepted only if all of these hold. Each is covered by the
portable specimen and can be re-run against any Ghidra build:

1. `8E D8` prints `MOV DS,AX` and writes DS.
2. Every `8E` register form (`C0`, `D0`, `E0`, `E8`, `C8`) prints the segment
   register first.
3. `8C D8` still prints `MOV AX,DS` and writes AX.
4. The memory forms (`8E 1E`, `8C 1E`) are unchanged.
5. `66 8E D8` prints `MOV DS,EAX`; `66 8C D8` prints `MOV EAX,DS`.
6. In long mode, `48 8E D8` prints `MOV DS,RAX` and `4D 8E C0` prints
   `MOV ES,R8`.
7. Instruction length and p-code are unchanged for every case.
8. A `CS`-loading encoding still decodes, still prints segment-first, and is
   still recognisable as a reserved encoding (the language does not reject it).

## Consequence for this project

The pinned 12.1.4 build keeps the reversed text, so:

* every segment-register instruction cited in a campaign report is quoted from
  the original bytes, not from a listing;
* semantic claims about such an instruction are supported by p-code or by an
  independent decoder;
* when the project moves to 12.2 or later, previously captured listings must be
  re-read rather than compared textually, because this exact text changes.

The trial installation is retained only for reproducing the table above. It is
not used for campaign evidence, and its projects are separate from the shared
installation's.
